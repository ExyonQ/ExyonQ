# AP-04 — External authorization (`auth_request`-style)

ExyonQ delegates the authorization decision for a route to an absolute HTTP
endpoint. The endpoint is called with `GET` before route access, with no client
body and with a bounded timeout.

```toml
[modules.auth.routes.api]
auth_request = { endpoint = "http://127.0.0.1:9000/verify", timeout_ms = 2000 }
```

`endpoint` must be an absolute `http://` URI with a host and a path. `https://`,
relative URIs, userinfo (`http://user:pass@host/`) and a zero or greater than
30 s `timeout_ms` are rejected when the configuration is loaded. The v1 client
stack is HTTP-only, so terminating TLS in front of the auth service (loopback
sidecar or internal network) is the supported deployment shape; an HTTPS
endpoint is never accepted and then failed closed at request time.

The endpoint receives the original end-to-end request headers (never `Host`,
`Content-Length`, `Connection`-nominated fields, hop-by-hop headers or the
client body) plus:

- `X-ExyonQ-Original-URI` — path and query, for example `/api/orders?page=2`
- `X-ExyonQ-Original-Method` — the client method, even though the subrequest is `GET`
- `X-ExyonQ-Original-Host` — the literal client `Host` header, including a
  non-default port (for example `api.example:8443`)

Client-supplied copies of those three names, and of the response identity names
`X-Auth-Request-User` and `X-ExyonQ-User`, are discarded before forwarding. Only
the values generated by ExyonQ cross the hop; a client cannot append a second
URI, method, host or user value for the auth service to trust.

Forwarded header values share an 8 KiB budget and at most 64 headers cross the
hop. `Authorization`, `Cookie` and other end-to-end fields are forwarded, which
is what makes bearer/JWT and session-cookie introspection work.

Response contract:

| Endpoint result | Client result |
| --- | --- |
| `2xx` | request continues; optional `X-Auth-Request-User` / `X-ExyonQ-User` becomes `$remote_user` for rate-limit keys |
| `401` | `401`; a valid `WWW-Authenticate` value is forwarded |
| `403` | `403` |
| timeout, transport error, any other status | `503` (fail closed) |

The subrequest timeout covers the connect and response headers. A short,
bounded cleanup read (100 ms, at most 64 KiB) lets the connection be reused
without letting a trickling auth server pin the request. Every other status —
including redirects, `404` and `5xx` — is an unavailable decision, not an
allow.

`auth_request` cannot be combined with `realm`/`user_file` on the same route.
Routes with external auth are forced onto the full Hyper dispatch path, so the
wire and static fast paths cannot bypass the check. The client body is not
forwarded; this surface validates bearer/JWT/cookie credentials, it is not a
request-signing proxy.

## JWT/OAuth pattern

The endpoint is the integration point for an introspection or verification
service. A minimal service contract:

```text
GET /verify
Authorization: Bearer <token>
X-ExyonQ-Original-URI: /api/orders
X-ExyonQ-Original-Method: GET
X-ExyonQ-Original-Host: api.example

200 + X-Auth-Request-User: alice   -> allow, rate-limit key user=alice
401 + WWW-Authenticate: Bearer     -> challenge the client
403                                -> deny
```

The same pattern covers opaque-token introspection (the endpoint calls the
identity provider), local JWT signature/claim validation, and cookie-session
lookup. ExyonQ does not parse JWT itself and does not cache decisions: each
request is authorized by the configured endpoint.

## Migrating nginx `auth_request`

nginx uses a relative internal location; ExyonQ requires the resolved endpoint:

```nginx
location = /_auth {
    internal;
    proxy_pass http://127.0.0.1:9000/verify;
    proxy_set_header X-Original-URI $request_uri;
}
location /api/ {
    auth_request /_auth;
    proxy_pass http://backend;
}
```

becomes:

```toml
[modules.auth.routes.api]
auth_request = { endpoint = "http://127.0.0.1:9000/verify", timeout_ms = 2000 }
```

The importer does not invent an upstream address for a relative
`auth_request /auth` location, so that directive remains a manual migration
step. `auth_request_set`, `proxy_set_header` inside the auth location and
`error_page 401 = @login` are not imported either; reproduce the needed
behavior in the auth service or in ExyonQ route configuration.

## Limits

- HTTP endpoints only; TLS client connections are out of scope for the v1
  proxy client stack.
- No request body, no response body and no response headers other than
  `X-Auth-Request-User` / `X-ExyonQ-User` and `WWW-Authenticate` are propagated.
- No decision cache; the endpoint sees every protected request.
- nginx `auth_request` is not mapped automatically from a relative location.
