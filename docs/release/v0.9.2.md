## WordPress real-browser journey

`scripts/gates/wordpress-browser-e2e.sh [image@sha256:digest] [outdir]` starts the
published WordPress image, waits for the installer and hands the real user
journey to a headless Chromium (`mcr.microsoft.com/playwright:v1.65.1-noble`,

## Blockers

1. **Docker Hub mirror.** `dockerhub-mirror` is part of the image contract
   (AGENTS.md §9) and fails closed when the repository secrets are missing; the
   repository currently has none. Fix: add `DOCKERHUB_USERNAME` and
   `DOCKERHUB_TOKEN` (read/write token) in *Settings → Secrets and variables →
   Actions*, then `gh run rerun 44404288845 --failed`. That run republishes
   nothing that already exists — the mirror copies the exact GHCR index
   digests — and lets `github-release` run.
2. **`github-release` never ran in CI.** It needs `dockerhub-mirror`, so the
   Release was built from the same run `44404288845` artifacts with that job's
   layout and verified with `scripts/release/verify-checksums.sh`
   (`INTEGRITY_VERIFIED=YES`). The SSH signature layer was added afterwards (see
   *Signing status*); the cosign layer that the trust policy still requires for
   an official release is absent, and the tag is unverified on GitHub because no
   signing key is registered to a GitHub account.

3. **Signed tag, attached matrix and stability declaration.** The DoD lists
   seven conditions for the stable release; three of them are still owner work:
   the tag `v0.9.2` is annotated but unsigned, the COMPAT matrix is not attached
   to the Release, and no stability declaration has been signed off.

## Stability declaration

**0.9.2 is published, verified and measured. It is not declared stable.** What
follows is what an operator may rely on today and what stays out of the promise;
items that are still missing are named, not implied.

### Promised

1. **Config compatibility promise V1** for the native IR configuration, as
   written in [docs/compat/config-compatibility-promise-v1.md](../compat/config-compatibility-promise-v1.md):
   a config that validates on a published 0.9.x release keeps validating on
   later 0.9.x releases; `config_version` only moves with a migration;
   unknown keys are rejected with the field named. Verified with the released
   binary: the literal `v0.9.1` config validates and the unknown-key control is
   rejected (`RESULT=PASS previously published configs still validate`).
2. **The three importer matrices over their declared corpus.** Measured from the
   binaries unpacked from this Release, on macOS arm64, Linux arm64 and Linux
   amd64: NGINX `exact=79 approximated=13 unsupported=5 directives=21`, Apache
   `0/1/0/17`, OpenLiteSpeed `9 fields`, with `P1_OPEN=0 P2_OPEN=0` and
   `RESULT=PASS COMPAT_MATRICES_GATE` on all three. The asset
   `COMPAT_MATRIX_v0.9.2.md` is attached to this Release and
   [docs/compat/COMPAT_MATRIX_v0.9.2.md](../compat/COMPAT_MATRIX_v0.9.2.md)
   carries the provenance, commands and the contrast against each published
   claim.
3. **Reproducible artifact identity**: the nine binaries are attached with
   `SHA256SUMS.txt` covering every asset except the sums file itself, and the
   downloaded assets re-verify (`INTEGRITY_VERIFIED=YES`).
4. **Image identity**: `ghcr.io/exyonq/exyonq:0.9.2` and
   `ghcr.io/exyonq/exyonq-wordpress:0.9.2` are multi-arch indexes verified by
   digest, with the per-arch digests recorded below.

### Not promised

- **Total nginx or Apache substitution.** `TOTAL_COMPAT_PROMISE` stays
  **FORBIDDEN** for those sources; the matrix measures a declared corpus, and
  every approximated or refused directive stays listed in
  `tests/fixtures/compat-matrix/gaps.txt`. Directives outside that corpus are
  not covered.
- **Runtime behaviour of an imported config.** The matrix is importer output;
  serving it is covered by the E2E suites, not by this document.
- Importers reading Apache/NGINX configuration at runtime (they are offline
  only), OpenLiteSpeed beyond one `perClientConnLimit` block, and any Windows
  build (there is none).
- macOS on anything but arm64, and the amd64 Linux binaries on a glibc older
  than 2.42 (see the limitation below).
- Undocumented keys, CLI output formats, diagnostic wording, downgrade paths and
  migrations across a major version bump.

### Signing status

The release is signed with the project's SSH ED25519 release key
`EXYONQ_RELEASE_TAG_SSH_V2` (fingerprint
`SHA256:7sMmeEgNFoOZa3xvaMgJPs4T724wWxiWMaFfW3Iusfs`), whose public half is the
trust root versioned in `security/signing/`:

- **Tag** `v0.9.2` → object `648cf617…`, annotated and SSH-signed. Harness:
  `bash scripts/release/verify-tag-signature.sh --repo . --tag v0.9.2
  --expected-version 0.9.2 --expected-commit 4e3338a… --allowed-signers
  security/signing/exyonq-release-tag-signers` → `Good "git" signature for
  exyonq-release with ED25519 key SHA256:7sMme…`, `TAG_SIGNATURE_VERIFIED=YES`.
- **Checksums** `SHA256SUMS.txt` → `SHA256SUMS.txt.sig`, namespace `file`,
  principal `exyonq-release`, attached to the Release. Verified against the
  downloaded bytes: `Good "file" signature for exyonq-release with ED25519 key
  SHA256:7sMme…`, `SSH_SIGNATURE_VERIFIED=YES`.

`scripts/release/verify-checksums.sh` still prints `AUTHENTICITY_VERIFIED=NO`
because it verifies integrity only and never inspects signatures; authenticity
is verified through the trust-root commands above, not by that flag.

**Not done: the cosign layer.** `security/signing/TRUST-POLICY.md` marks
`COSIGN_ARTIFACT_LAYER = RETAINED_REQUIRED_FOR_OFFICIAL_RELEASE` and cosign is
neither installed here nor provisioned with a private key, so the release has
the SSH layer only. The trust root is also still `LOCAL_ACTIVATION_ONLY` — the
public keys have not been published out of band — and GitHub will show the tag
as unverified because the key is not registered to a GitHub account.

### Why stability is not declared

The authenticity gap that blocked the previous declaration is closed for the SSH
layer: the tag and `SHA256SUMS.txt` carry signatures that verify against the
versioned trust root. Three conditions of the roadmap's stable-release item are
still not met, and none of them is mine to close: the cosign layer required by
the trust policy is absent, the full CI run (including E2E and CRS) has not been
re-executed on the tag commit, and the stability sign-off belongs to the release
owner. Declaring 0.9.2 stable would claim more than the evidence shows.

## Known limitations

- **glibc floor differs per architecture in the 0.9.2 binaries.** The
  `x86_64-unknown-linux-gnu` job ran on `ubuntu-latest`, which is now Ubuntu
  26.04 (glibc 2.42), while `aarch64-unknown-linux-gnu` ran on `ubuntu-24.04-arm`
  (glibc 2.39). Measured: the published amd64 binary aborts on Ubuntu 24.04 with
  `libc.so.6: version 'GLIBC_2.42' not found`, the arm64 binary runs natively
  there. The GHCR images are unaffected (Wolfi `glibc-dynamic`). The workflow
  pins `ubuntu-24.04` for the x86_64 build from the next run on, so the amd64
  tarball, `.deb` and `.rpm` keep a 2.39 floor; the already-published 0.9.2
  amd64 artifacts still need glibc ≥ 2.42.
- The WordPress **production-site** browser journey (the owner's live site with
  its own credentials and content) remains open and belongs to the owner. The
  container-level real-browser journey above is done on amd64 and arm64.
- The positive reCAPTCHA v3 path remains **NOT EXECUTED** without a real v3 key;
  no fake endpoint or relaxed validation is used. To execute it,
  `scripts/e2e/ol04-challenge-e2e.sh` needs all three of
  `OL04_RECAPTCHA_V3_SITE_KEY`, `OL04_RECAPTCHA_V3_SECRET` and a fresh
  `OL04_RECAPTCHA_V3_TOKEN` minted for action `challenge` with a score ≥ 0.5 by
  a site key whose allowed domains include the test host. Without all three the
  runner prints `NOT EXECUTED positive reCAPTCHA v3` and fails closed.
- No Windows build is produced, by policy.
- NGINX/Apache/OpenLiteSpeed compatibility remains the documented scope.
- Tag signature: `v0.9.2` is annotated but **unsigned** (`git tag -v` reports no
  signature). The audit gate binds the tag to the audited commit; it does not
  assert a signature.
