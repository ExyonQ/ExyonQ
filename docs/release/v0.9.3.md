## Why a patch release

The 0.9.2 artifacts embed `wasmtime` 49.0.5. The advisories
RUSTSEC-2026-0566 through RUSTSEC-2026-0572 are closed by 49.0.6, so the only
red left on the 0.9.2 release-condition 6 (CI on the tag) was the advisory set,
not the code. A patch that moves the pin is the smallest honest fix: no
behaviour change, no config or protocol change, no new dependency, no new
feature.

**Seal scope.** The seal's tracked component is the canonical `git diff` (the
seal-managed hash citations are normalized so the documents can contain the
final values), and its untracked component is a sorted manifest of every
untracked path with a content SHA-256. The combined fingerprint and the total
count (84 = 74 tracked + 10 untracked) therefore change when an untracked file
is added, removed or edited; a count alone is never sufficient. The seal's own
integrity block is excluded from its self-hash because it contains the hash,
but every other byte is covered. The embedded manifest is rehashed against
`WORKTREE_UNTRACKED_SHA256/FILES`, full and 8-hex citations use different
normalization tokens, and a citation check rejects a
`WORKTREE_FINGERPRINT_SHA256` line naming a different value.
`verify-release-audit.sh` reports both fingerprints and the changed untracked
path on failure.

## Before signing the tag: the two commits the seal gate requires (steps 7–8)

`scripts/verify-release-audit.sh 0.9.3` does not read the seal as prose. It parses the
`| **Commit** |` cell, resolves that SHA as a git commit object, and — when
`refs/tags/v0.9.3` exists — compares it with the tag. Exactly two shapes are accepted
(`--selftest` exercises both with real commits and tags: `PASS_EXPECT_PASS clean_audit` and
`PASS_EXPECT_PASS audit_seal`, RC 0):

| Shape | Seal `Commit` cell | Tagged commit | Difference between them |
| --- | --- | --- | --- |
| A — tag the audited commit | `C` | `C` | none |
| B — audited commit plus a seal-only commit | `C` | `S`, with `S^` = `C` | only `docs/security/audit-v0.9.3.md` |

Shape A cannot be produced for 0.9.3: `C`'s own tree would have to contain its own SHA, which
does not exist until the commit is written. So the patch is committed as **C**, the seal is
re-pointed in **S**, and **`v0.9.3` is tagged on S**, never on C.

1. **Commit the audited state as C.** It must carry exactly the bytes the seal describes: the
   seal's **74** modified files *and* its 10 untracked files (this seal,
   `docs/release/v0.9.3.md`, `docs/architecture/fastcgi-php-fpm-operations.md`, the four
   gate/release scripts and `supply-chain/`). The current tree is the re-audited 84-entry
   snapshot (`WORKTREE_FINGERPRINT_SHA256 = 89788d3c…`), not the retired 48-file snapshot. Committing a subset still passes the
   gate, but makes `AUDITED_STATE`/`WORKTREE_DIFF_SHA256` false — the verifier checks the
   binding, not the completeness of the audit. Stage explicit paths (never `git add -A`),
   commit, then `C=$(git rev-parse HEAD)`.
2. **Re-point the seal, in that file only.** Replace the abbreviated SHA in `| **Commit** |`
   with the full 40-hex of `C` (an abbreviation such as `0f58cae…`, or the `<full sha>`
   placeholder, fails with `CONTROL=commit_full_sha` / `CONTROL=commit_bind`), and update the
   prose block so it states the committed reality:

   ```text
   AUDITED_STATE        = C <40-hex> (the 0.9.3 patch commit)
   SEAL_COMMIT          = S <40-hex> (audit-only; first parent C; changes only the seal file)
   TAG                  = v0.9.3 (signed annotated tag on S)
   WORKTREE_FINGERPRINT_SHA256 = 89788d3c… (the pre-commit 84-entry worktree this seal was written
                          against on 2026-11-25, after #109, ACME/H3 and the strict verifier;
                          the old d0f7c01a… / 48-file snapshot is retired)
   ```

3. **Commit only the seal as S**, directly on top of `C` (no merge, so `S^` is `C`):
   `git commit -m "…" -- docs/security/audit-v0.9.3.md`, then `S=$(git rev-parse HEAD)`.
4. **Prove the shape before touching any tag:**

   ```bash
   git rev-parse "$S^"                          # must print C
   git diff --name-only "$C" "$S"               # must print exactly docs/security/audit-v0.9.3.md
   bash scripts/verify-release-audit.sh 0.9.3   # RELEASE_AUDIT_GATE=PASS (HEAD is S; no tag yet)
   ```

5. **Create the signed annotated tag on S, check the tag out, and re-verify** — all before
   pushing anything:

   ```bash
   git tag -s v0.9.3 -m "ExyonQ 0.9.3" "$S"
   git checkout --detach v0.9.3                  # the verifier reads the seal from the checkout
   bash scripts/verify-release-audit.sh 0.9.3    # takes the tag branch
   bash scripts/verify-release-audit.sh --selftest
   bash scripts/gates/tag-signature-gate.sh --tag v0.9.3 --expected-commit "$S"
   git checkout <branch>                         # back to the branch before pushing
   ```

   A local tag can still be deleted and re-created if one of these fails; a pushed tag cannot.

   **The checkout is part of the step, and this is why.** The verifier reads the seal from the
   working tree, not from the tagged tree, so its two halves are not interchangeable. Measured
   with this same script in a throwaway sandbox: tag on S with the tag checked out →
   `RELEASE_AUDIT_GATE=PASS`, RC 0; tag on C with the tag checked out → **RC 1**; but HEAD at S
   with the tag on **C** → **RC 0**, because the seal it reads is S's (which names C) while the
   tag resolves to C. That last run says nothing about the tag: always verify the tag from the
   tag.
6. **Then push** the branch and the tag. `release.yml`'s `security-release` job checks out with
   `fetch-depth: 0` and runs the same command with `GITHUB_SHA` set to the tag commit, so a tag
   that moved after this step fails there with `CONTROL=github_sha_mismatch`.

### Failure modes, and the fix for each

| Output | Cause | Fix |
| --- | --- | --- |
| `CONTROL=commit_full_sha` | Commit cell is abbreviated (`0f58cae…`) or a placeholder | Put the full 40-hex of C |
| `CONTROL=commit_bind` | Commit cell missing or still `<full sha>`/`X.Y.Z` | Restore the row with the real SHA |
| `CONTROL=commit_exists` | C is not an object in this clone (shallow checkout) | `git fetch --unshallow`, or `fetch-depth: 0` as the workflow already sets |
| `CONTROL=tag_mismatch` | The tag points at a commit that is neither the seal's Commit nor its first parent — for 0.9.3, tagging anything but S while the seal names C | Delete the local tag and tag S |
| `CONTROL=seal_diff` | The tagged commit differs from the seal's Commit by more than the seal file. The classic case is tagging C while the seal at C still names its parent `0f58cae`, so the rest of the patch shows up in the diff; the same code fires if S carries a `CHANGELOG.md` or release-note edit | Move those edits into C and tag S, the commit that changes only the seal |
| `CONTROL=github_sha_mismatch` | CI checked out a different commit than the tag | Re-tag the intended S; never move a pushed tag |
| `CONTROL=blockers_empty` | `## Blockers` is not empty/`None` | Close the blocker; do not blank the section |

The pre-tag run in step 4 passes whenever the Commit cell names *any* existing commit: it proves
the cell is well formed and says nothing about the tag. Only the step 5 run, made from the tag's
own checkout, proves the shape that `release.yml` enforces on CI.

## How the signature is checked from now on

`scripts/gates/tag-signature-gate.sh` is the repeatable entry point around
`scripts/release/verify-tag-signature.sh` (annotated tag, authorized principal,
exact commit, version match, SSH signature against
`security/signing/exyonq-release-tag-signers`). It runs in:

- `cargo run -p xtask -- ci` — on a branch it prints `RESULT=NOT_APPLICABLE`
  (exit 0, never a pass); on a tagged tree it fails closed. The same command
  runs the gate's `--selftest`, so the gate cannot silently go vacuous.
- `.github/workflows/release.yml` — step `Verify release tag signature`, before
  any artifact is built, with `--tag vX.Y.Z --expected-commit ${{ github.sha }}`.
- The release checklist above, step 8.
