## 1. Before the fix

Both release attempts failed at the GHCR push, not at the build:

| Release | Run | Failure |
| --- | --- | --- |
| v0.9.0 | `41361024701` | 2026-11-02T00:54:30Z `denied: permission_denied: write_package` |
| v0.9.1 | `42247244600` | 2026-11-06T17:45:18Z `denied: permission_denied: write_package` |

Package settings showed `Manage Actions access` → `ExyonQ/ExyonQ` →
`Role: Read` for both `exyonq` and `exyonq-wordpress`. `Read` allows pulls only;
publishing a version requires `Write`. The ACL has no REST/GraphQL endpoint, so
it was changed in the package settings UI and verified by reloading the page.

Procedure and rationale: `docs/governance/ghcr-image-publish-permissions.md`.

### 7.3 WordPress runtime

The tracked gate `scripts/gates/wordpress-container-e2e.sh` targets the 0.9.2
tree and cannot run unmodified against 0.9.1: 0.9.1 ships the cache client as a
mu-plugin (`wp-content/mu-plugins/exyonq-cache/`), while the gate asserts a
normal plugin under `wp-content/plugins/exyonq-cache`. The same journey was run
with the gate's config (`full_page_cache.key.query = ["p"]`) and its restart
ordering, asserting the mu-plugin layout instead.

| Check | Result |
| --- | --- |
| Installer `200`, WordPress install, 8 non-empty salts | PASS |
| Login, `wp-admin` dashboard `200` | PASS |
| mu-plugin loader + client dir, no normal plugin copy | PASS |
| Purge socket reachable | PASS |
| Purge `status_probe` after restart | **FAIL** — `{"configured":true,"reachable":true,"auth":"rejected","error":"unauthenticated"}` |
| Anonymous FPC `miss` → `hit` | PASS |
| Cached nonce accepted by a second anonymous client | PASS |
| Logged-in request: `x-cache: bypass`, `x-cache-reason: cookie_denied` | PASS |
| Versions | WordPress 7.1.4, PHP 8.5.12 |

**Root cause (real defect in the 0.9.1 image).** The entrypoint generates a new
`EXYONQ_CACHE_PURGE_TOKEN` on every boot and writes it into `wp-config.php` only
when that file is created. After a restart the server uses the new token while
the mu-plugin reads the old define from `wp-config.php`, so every purge is
rejected. The working tree fixes it: `packaging/docker/wordpress/entrypoint.sh`
now reuses the token already present in `wp-config.php` and does not regenerate
it. Without a restart the probe reports `auth: accepted`, which is why the
earlier local run did not surface this.

The fleet consequence is limited to the published 0.9.1 WordPress image: a
restarted container keeps serving and caching but cannot invalidate pages on
publish. It is not claimed as fixed in 0.9.1.
